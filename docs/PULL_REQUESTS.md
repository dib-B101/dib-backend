# Pull Request 작성 가이드

이 문서는 `dib-backend` 저장소의 Pull Request 제목과 본문 작성 규칙이다.
PR 본문은 리뷰어가 변경 목적, 실제 구현 범위, API 계약과 검증 결과를 한 번에 확인할 수 있도록 작성한다.

## 제목

PR 제목은 영문 Conventional Commit 타입과 한글 설명을 사용한다.

```text
<type>(<optional-scope>): <한글 설명>
```

예시:

```text
feat(auth): 일반 로그인 기능 구현
fix(member): 중복 닉네임 검증 오류 수정
```

## 본문 작성 원칙

- 첫 문단에서 사용자 또는 시스템 관점의 결과를 설명한다.
- 주요 변경사항은 번호가 있는 소제목으로 나누고, 각 항목에 구현 내용과 의도를 함께 적는다.
- 코드와 실제 동작을 기준으로 작성하며 구현하지 않은 기능은 포함하지 않는다.
- API가 변경되면 메서드, 경로, 요청·응답 예시와 주요 오류를 기록한다.
- 토큰, 세션, 개인정보처럼 보안과 관련된 값은 저장 방식과 노출 범위를 명확하게 구분한다.
- 실행한 테스트와 결과를 적는다. 실행하지 못한 검증은 성공한 것처럼 표현하지 않고 사유를 남긴다.
- 외부 API·오류 코드·제품 명세의 후속 수정이 필요하면 `명세서 반영 사항`에 분리한다.
- 해당하지 않는 선택 섹션은 빈 상태로 남기지 말고 제거한다.

## 표준 형식

아래 형식을 기본으로 사용한다. 바깥쪽 네 개의 백틱은 이 문서에서 템플릿 전체를 보여주기 위한 것이므로 실제 PR 본문에는 포함하지 않는다.

````markdown
## 개요

{변경 목적과 완료된 결과를 1~3문장으로 설명합니다.}

## 주요 변경사항

### 1. {변경 영역}

* **{핵심 변경}:** {구체적인 구현 내용과 이유}
* **{핵심 변경}:** {구체적인 구현 내용과 이유}

### 2. {변경 영역}

* **{핵심 변경}:** {구체적인 구현 내용과 이유}

---

## API 명세

### Request

```http
POST /api/v1/{resource}
Content-Type: application/json

{
  "field": "value"
}
```

### Response

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "field": "value"
}
```

## 오류 처리

| HTTP 상태 | 오류 코드 | 발생 조건 |
| --- | --- | --- |
| `400` | `{ERROR_CODE}` | {오류가 발생하는 조건} |

## 테스트

* **자동 테스트:** `{실행 명령}`
* **검증 결과:** {통과한 테스트 수 또는 확인한 동작}

## 명세서 반영 사항

* {API 또는 공통 오류 코드 명세에 반영할 내용}
````

API 변경이 없는 PR은 `API 명세`와 `오류 처리`를 제거한다. 명세서 수정이 필요하지 않으면 `명세서 반영 사항`을 제거한다.

## 작성 전 확인

- PR 대상 브랜치와 실제 diff가 의도한 범위인지 확인한다.
- 요청·응답 필드명, 상태 코드, 오류 코드가 구현과 일치하는지 확인한다.
- 환경 변수 값, 토큰 원문, 전화번호 등 비밀값이나 개인정보가 예시에 포함되지 않았는지 확인한다.
- 테스트 명령과 결과가 최신 커밋을 대상으로 한 것인지 확인한다.
- 관련 문서와 인수 조건의 변경 여부를 확인한다.
